# 5. Priority Queue Implementation

In a standard FIFO (First-In, First-Out) queue, every job is treated equally. But in the real world, some tasks are significantly more urgent than others. For example, a "Password Reset Email" (high priority) should be processed immediately, even if there are 10,000 "Weekly Newsletter Emails" (low priority) already waiting in the queue.

A **Priority Queue** ensures that urgent jobs always jump to the front of the line.

## 1. The Implementation Strategies

There are two primary ways to build a priority queue in Redis:

### Strategy A: Redis Sorted Sets (`ZADD` / `ZPOPMIN`)
* **How it works:** You put every job into a single Redis Sorted Set and assign it a "score" (e.g., High = 1, Normal = 2, Low = 3). Redis constantly sorts the set by this score.
* **Pros:** Highly dynamic. You can have 100 different priority levels.
* **Cons:** Slower. Inserting into a sorted set is $O(\log(N))$, and you cannot easily "block" (wait) for a specific score to arrive without complex workarounds.

### Strategy B: Multiple Lists (The `QueueFlow` Approach)
* **How it works:** Instead of one queue, you create three completely separate Redis Lists: `jobQueue:high`, `jobQueue`, and `jobQueue:low`.
* **Pros:** Blazing fast. `LPUSH` is $O(1)$. More importantly, you can use `BRPOP` to block and listen to all three lists simultaneously in a strict, guaranteed order.
* **Cons:** You are limited to the specific priority levels you created keys for (which is almost always perfectly fine for real-world apps).

## 2. The `BRPOP` Magic

The secret weapon of `QueueFlow`'s priority system is how the `BRPOP` command handles multiple keys.

```bash
BRPOP jobQueue:high jobQueue jobQueue:low 0
```

When you pass an array of keys to `BRPOP`, Redis guarantees that it will evaluate them from **left to right**.
1. It checks `jobQueue:high`. If there is a job, it pops it and returns immediately.
2. If `jobQueue:high` is empty, it checks `jobQueue`.
3. If both are empty, it checks `jobQueue:low`.
4. If all three are empty, it puts the connection to sleep (blocks) until a job arrives in *any* of them.

If a worker is sleeping and a job suddenly arrives in `jobQueue:low`, it wakes up and grabs it. But if a job arrives in `jobQueue:high` at the exact same millisecond, the worker will grab the `high` job first because of the strict left-to-right evaluation order.

## ⚡ Application in QueueFlow Project

Here is exactly how this is implemented in your codebase:

**1. The Enum Definition (`queues.js`)**
You define the valid priorities and their corresponding Redis keys:
```javascript
const PRIORITIES = {
  HIGH: 'high',
  NORMAL: 'normal',
  LOW: 'low'
};

// The exact order for BRPOP
const QUEUES_IN_PRIORITY_ORDER = [
  'jobQueue:high',
  'jobQueue',       // normal is the default
  'jobQueue:low'
];
```

**2. The Producer (`app.js`)**
When a job is created, the API checks the requested priority and routes it to the correct Redis key:
```javascript
// Defaults to 'normal' if none provided
const targetQueue = queues.queueKeyForPriority(priority); 
await redis.lPush(targetQueue, JSON.stringify(jobPayload));
```

**3. The Consumer (`worker.js`)**
The worker passes the entire array to `BRPOP`:
```javascript
const result = await redis.brPop(queues.QUEUES_IN_PRIORITY_ORDER, 0);
```

## 🎤 SDE1 Interview Questions & Answers

### Q1: "How did you implement priority queuing, and why did you choose that approach?"
**Answer:** "I implemented priority queuing by using multiple Redis Lists—specifically a high, normal, and low queue. When a job is created, the Express API pushes it to the specific list matching its priority. I chose this approach over using a single Redis Sorted Set because it allowed me to utilize the `BRPOP` command. `BRPOP` accepts multiple keys and guarantees left-to-right evaluation, meaning I get strict priority ordering with $O(1)$ insertions and zero-CPU blocking, which is significantly more efficient than constantly re-sorting a single massive queue."

### Q2: "What happens to low priority jobs if there is a constant, never-ending stream of high priority jobs?"
**Answer:** "This is a classic problem called **Starvation**. If high-priority jobs never stop arriving, the worker will never reach the `jobQueue:low` list, and those jobs will sit there forever. In a production environment with massive scale, I would solve this by either dedicating a specific worker *only* to the low-priority queue to guarantee throughput, or by implementing an 'aging' mechanism where a background script periodically upgrades low-priority jobs to normal priority if they have been waiting for longer than a certain threshold."

### Q3: "If you wanted to add a 'critical' priority level above 'high', how difficult would that be to change in your architecture?"
**Answer:** "It would be incredibly simple and require almost no code changes. Because my priority system is just an array of Redis keys, I would simply add `'jobQueue:critical'` to the beginning of the `QUEUES_IN_PRIORITY_ORDER` array in my configuration file, and add `'critical'` to my validation enum. The `BRPOP` command would automatically start evaluating the critical queue first."
