# 6. Failure Handling & Exponential Backoff

In a distributed system, failures are not just possible—they are guaranteed. Databases will lock, external APIs will rate-limit you, and network packets will drop. A robust job queue must assume that jobs will fail and have a rock-solid strategy for handling those failures without losing data.

## 1. Why Jobs Fail & Idempotency

When a job fails, the immediate response is to retry it. However, retrying introduces a massive danger: **what if the job partially succeeded before failing?**

Imagine a "Process Payment" job. It successfully charges the user's credit card, but then the database connection drops before it can save the receipt. If the queue blindly retries the job, it will charge the user's credit card a second time. 

This is solved by **Idempotency**—designing jobs so that they can be safely executed multiple times without changing the result beyond the initial application. In QueueFlow, we handle this by tracking the exact state of every job in the PostgreSQL database.

## 2. Exponential Backoff

If an external API (like SendGrid for emails) goes down, immediately retrying the job 3 times in the same millisecond will just result in 3 instant failures. You need to give the failing service time to recover.

**QueueFlow uses Exponential Backoff.** Instead of fixed delays, the wait time increases exponentially after every failure.

### The Math: `delay = base_delay * (2 ^ retry_count)`

In your `worker.js`, the logic is implemented exactly like this:
```javascript
// Base delay is 2000ms (2 seconds)
const backoffMs = 2000 * (2 ** retry_count); 
```

1. **Failure 1 (retry_count = 0):** `2000 * (2^0)` = 2 seconds
2. **Failure 2 (retry_count = 1):** `2000 * (2^1)` = 4 seconds
3. **Failure 3 (retry_count = 2):** `2000 * (2^2)` = 8 seconds

If the job fails for a 4th time (exceeding `max_retries = 3`), it is marked as permanently failed.

### Durable Non-Blocking Retries (ZSETs)
When a job needs to wait 8 seconds for its next retry, the worker **does not sleep for 8 seconds**. That would block the entire queue! 
Historically, developers used `setTimeout` for this, but if the Node.js server crashes during those 8 seconds, the job is wiped from RAM and lost forever.

Instead, QueueFlow achieves **100% durable delays** using Redis Sorted Sets (`ZSET`). The worker calculates the exact UNIX timestamp when the job should run again, stores it in Redis, and instantly moves on to the next job:
```javascript
async function scheduleRetry(redis, job, delayMs) {
  const score = Date.now() + delayMs;
  await redis.zAdd(DELAYED_QUEUE, [{ 
    score, 
    value: JSON.stringify(job) 
  }]);
}
```
A maintenance loop runs on every worker iteration (up to every 5 seconds), using `ZRANGEBYSCORE` to find jobs whose timestamps have expired, and moves them back into the active lists.

## 3. The Dead Letter Queue (DLQ)

When a job exceeds its maximum retries, it is permanently marked as `status = 'failed'` in PostgreSQL. 

In enterprise systems, this permanently failed state is often referred to as a **Dead Letter Queue (DLQ)**. The DLQ is not actually a queue that processes things; it is a resting place for poisonous or broken jobs.

In QueueFlow, the DLQ is simply all jobs in the database where `status = 'failed'`. 
Engineers can monitor the DLQ, fix the underlying bug in the code, and then manually click the "Retry" button on the dashboard to put the job back into the pipeline.

## 🎤 SDE1 Interview Questions & Answers

### Q1: "If your worker crashes in the middle of processing a job, how does your system recover it?"
**Answer:** "Because I track the job state in PostgreSQL, if a worker abruptly dies, the job will be permanently stuck with a `processing` status. To fix this, I built a 'Reaper' maintenance loop into the worker that runs every 15 seconds. It scans PostgreSQL for jobs stuck in `processing` for longer than 60 seconds. The loop instantly resets their status back to `queued` and re-pushes them to Redis so a healthy worker can pick them up."

### Q2: "Why did you choose Exponential Backoff instead of just waiting 5 seconds between every retry?"
**Answer:** "Fixed delays are dangerous in distributed systems. If a downstream service goes down and 1,000 jobs fail simultaneously, a fixed 5-second delay guarantees that all 1,000 jobs will retry at the exact same millisecond 5 seconds later, creating a 'Thundering Herd' that will immediately crash the service again. Exponential backoff naturally staggers the retries and gives the downstream service breathing room to recover."

### Q3: "How did you ensure that delayed jobs aren't lost if your server crashes during their backoff period?"
**Answer:** "In a naive implementation, developers use `setTimeout` to wait before retrying, but that holds the job in volatile RAM. If the server crashes, the timer is destroyed and the job is permanently lost. I solved this by implementing a durable delayed queue using Redis Sorted Sets (`ZSET`). When a job fails, I calculate its exact execution timestamp and `ZADD` it to Redis. A background loop polls this set using `ZRANGEBYSCORE`. Because the delay state is held externally in Redis, I can restart my Node.js servers a thousand times and never lose a single pending retry."
